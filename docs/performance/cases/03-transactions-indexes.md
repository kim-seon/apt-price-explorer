# 사례 03. 거래 테이블 인덱스 — 쿼리 패턴 2개, 인덱스 2개, 용량 예산 안에서

- 날짜: 2026-10-18
- 대상: 거래 테이블(5,144,081건)을 읽는 화면별 대표 쿼리 11개 + 적재 파티션 삭제
- 환경: 로컬 Docker PostgreSQL 17, 수도권 전체 적재 후 `VACUUM FULL` · `ANALYZE`, JIT 기본값(on)
- 재현: `pnpm bench:queries --runs 7` (쿼리 정의: `scripts/bench-queries.ts`), 계획: `--explain <이름>`

## 문제

전체 적재가 끝나 인덱스를 설계할 시점이 됐다 (지금까지는 PK만, CLAUDE.md 10). 두 가지 증상이 있었다.

1. **화면**: 운영(Neon 0.25 CU)에서 단지 상세 응답 완료까지 2.8초, 지역 화면 1.4~2.2초.
2. **정기 갱신**: 파티션 하나 삭제가 로컬 320ms, Neon 900ms. 매일 갱신(581개 파티션)이 28.7분 걸렸고, 매월 24개월 재수집(1,992개)은 약 84분으로 **워크플로 제한(60분)을 넘는다**.

baseline은 모든 쿼리가 130~260ms로 비슷했다. 계획을 보면 전부 `Parallel Seq Scan`으로 514만 행을 읽고 99.9% 이상을 버린다 (헬리오시티 84㎡ 거래 791건을 찾으려고 514만 행 스캔).

## 조회 패턴 → 후보

| 패턴 | 쿼리 | 후보 |
|---|---|---|
| 단지 하나 | 단지 상세 3개, 지역 단지 목록(단지별 집계) | `(apt_seq, area_type_label, deal_date)` |
| 시군구 + 기간 | 지역 통계 · 요약, 거래 탐색(계약일 정렬 · 건수), 파티션 삭제 | `(sgg_code, deal_date)` |

열 순서: 같음 조건(`apt_seq`, `sgg_code`)을 앞에, 범위 · 정렬(`deal_date`)을 뒤에.

## 결정: 복합 인덱스 대신 `(apt_seq)` 단일 열

| 인덱스 | 크기 | 단지 상세 쿼리 |
|---|---:|---|
| `(apt_seq, area_type_label, deal_date)` | 170MB | 0.9 / 5.7 / 2.2ms |
| **`(apt_seq)`** | **36MB** | 0.9 / 5.9 / 2.4ms |

속도는 같고 크기는 1/5이다. 단지 하나의 거래는 많아야 수천 건이라, 인덱스로 단지를 찾은 뒤 면적 타입 · 날짜는 heap에서 걸러도 충분하다. `apt_seq`는 값마다 평균 260건이 중복돼 B-tree 중복 제거(deduplication)가 크게 작동한다. `(sgg_code, deal_date)`도 같은 이유로 51MB에 그친다.

**이 차이가 중요한 이유**: 운영 DB는 Neon Free(1GB). 복합 인덱스면 합계 221MB, 단일 열이면 87MB.

`region.monthlyStats`(110ms)는 시군구 전체 기간(약 9만 건)을 읽어 분위수를 계산한다. 인덱스로 줄일 수 있는 범위는 여기까지이고, 더 줄이려면 월별 사전 집계(갱신 비용 · 신선도 trade-off)가 필요하다 — Phase 2 후보.

## 남은 일 / trade-off

- **운영 반영 순서**: `LATERAL`로 바꾼 쿼리는 인덱스가 없으면 단지마다 전체 스캔이 된다. Neon에 마이그레이션 0002를 먼저 적용한 뒤 배포한다.
- **용량**: Neon은 매일 갱신의 삭제분(dead tuple 약 58만 행)까지 포함해 930MB였다. +87MB면 1GB를 넘어, Neon을 비우고 로컬(인덱스 포함)에서 재복원했다 → 915MB. 갱신 워크플로에 용량 감시(`pnpm db:size`, 900MB 경고 · 950MB 실패 알림)를 붙였다 (0002).
- **운영 Neon PK 인덱스**: 복원 중 점진적으로 만들어져 146MB(로컬 재생성 110MB). REINDEX로 36MB를 줄일 수 있지만, 작업 중 임시 공간이 필요해 1GB 근처에서는 보류.
- **JIT**: 짧은 조회 쿼리에서 컴파일 비용(139ms)이 실행 시간(40ms)보다 커서 DB 단위로 껐다 (0003). 큰 집계 쿼리(`region.monthlyStats`)는 JIT 이득이 있었으나 차이는 작다(110 → 104ms, 오히려 빨라짐 — 측정 편차 범위).
- **쓰기 비용**: 인덱스 2개가 INSERT를 느리게 하지만, 최근 7개월 재수집(581개 파티션)은 로컬 기준 **2.0분**(파티션 삭제 6~8ms). 인덱스 전 Neon 28.7분 — 운영 재측정은 다음 정기 갱신에서.
