# 사례 04. 거래 표 가상화 — 비용이 "불러온 행 수"에 비례하던 것을 상수로

- 날짜: 2026-10-19
- 대상: 지역 거래 탐색 표(무한 스크롤), 단지 상세 거래 내역 표
- 환경: 로컬 프로덕션 빌드(`next start`), 로컬 PostgreSQL(514만 건, 인덱스 적용 — 사례 03)
- 도구: TanStack Virtual 3.14.13 (`useWindowVirtualizer` / `useVirtualizer`)

## 먼저 확인한 것: 서버(offset)는 병목이 아니다

docs/03 Decisions 1-1은 "offset으로 시작 → 깊은 스크롤 저하를 측정 → 확인되면 keyset 전환"이었다. 송파구 전체 기간(91,464건)으로 offset별 API의 DB 시간을 쟀다.

| offset | 0 | 1,000 | 10,000 | 30,000 | 60,000 |
|---|---:|---:|---:|---:|---:|
| 로컬 (ms) | 18 | 15 | 18 | 37 | 25 |
| 운영 Neon (ms) | 51~55 | 40~42 | 56~66 | 48~50 | 49~55 |

offset 3만(100건씩 300번 불러온 지점)에서도 수십 ms다. 운영은 Vercel ↔ Neon 왕복이 대부분이라 offset과 관계없이 일정하다. **keyset 전환은 하지 않는다** — 잃는 것(임의 정렬 열에서의 커서 구현 복잡도, 페이지 위치 개념)에 비해 얻는 것이 없다.

## 문제: 클라이언트 비용이 불러온 행 수에 비례

같은 화면에서 스크롤로 행을 쌓으며 쟀다 (CPU 4배 감속, headless Chrome + CDP).

| 불러온 행 | DOM 노드 | JS heap | 다음 페이지 로드+렌더 | 최대 long task |
|---:|---:|---:|---:|---:|
| 100 | 1,388 | 8MB | - | - |
| 1,000 | 12,355 | 19MB | 407ms | 102ms |
| 3,000 | 36,424 | 42MB | 775ms | 284ms |
| 5,000 | 60,471 | 108MB | 1,166ms | 448ms |

필터 변경(5,000행 상태 → 기간 1년): 클릭 후 **첫 시각 반응(이전 결과 흐리게)까지 1,164ms**. 이유는 두 가지다.

1. 페이지가 추가될 때마다 기존 행까지 전부 다시 렌더 → 페이지당 비용이 O(누적 행)
2. 보이지 않는 행도 모두 DOM에 있음 → 필터 변경 시 수천 행의 스타일 변경 · 재렌더

## 선택지

| 안 | 해결 | 남는 것 |
|---|---|---|
| A. 행 컴포넌트 memo | 1 (추가 페이지만 렌더) | DOM 6만, 필터 변경 비용, 메모리 |
| **B. 가상화** | 1 + 2 | Ctrl+F가 화면 밖 행을 못 찾음, 행 높이 측정 필요 |

B를 택했다. CLAUDE.md 5의 "TanStack Virtual — 데이터 규모상 실제 필요할 때"의 조건이 측정으로 확인됐다(1,000행부터 long task 100ms 초과).

## 구현

- `<table>` 구조와 접근성을 유지한다: 보이는 행 위아래에 높이만 가진 빈 행(spacer)을 두고, `aria-rowcount` · `aria-rowindex`로 전체 행 수와 위치를 알린다.
- `table-layout: fixed` + 열 너비 고정: 보이는 행이 바뀌어도 열 폭이 흔들리지 않는다.
- 행 높이는 `measureElement`로 실제 측정한다 (모바일은 단지명 아래 줄이 있어 높이가 다르다).
- 거래 탐색: 창 스크롤 기준(`useWindowVirtualizer`), 표 본문의 문서 위치를 `scrollMargin`으로 준다. 무한 스크롤 감지(IntersectionObserver)는 그대로.
- 단지 상세: 표 자체 스크롤 영역(`useVirtualizer`), sticky 헤더 높이만큼 `scrollMargin`.
- **키보드**: 화면 밖 행은 DOM에 없어 Tab으로 이어 갈 수 없다 → 행에서 ↑ / ↓로 이동하면 해당 행으로 스크롤 후 포커스 (테이블 → 차트 하이라이트 연동 유지).

## 결과

거래 탐색 (같은 측정, CPU 4배 감속):

| 불러온 행 | DOM 노드 | JS heap | 다음 페이지 | 최대 long task |
|---:|---:|---:|---:|---:|
| 1,000 | 12,355 → **737** | 19 → **9MB** | 407 → **125ms** | 102 → **59ms** |
| 5,000 | 60,471 → **736** | 108 → **11MB** | 1,166 → **129ms** | 448 → **60ms** |

필터 변경 첫 반응: **1,164ms → 33ms**, 새 결과 렌더 완료 1,640 → 75ms. 행 수와 무관하게 일정하다.

단지 상세 (파크리오 84㎡ 전체 기간 2,966행, Lighthouse 모바일 프리셋 · devtools 스로틀링 · 3회 중앙값, 같은 데이터로 이전 빌드와 비교):

| | Before | After |
|---|---:|---:|
| Performance | 64 | **85** |
| LCP | 2,669ms | **2,028ms** |
| TBT | 2,215ms | **517ms** |
