# 사례 05. 정기 갱신이 운영 DB를 하루 60MB씩 키우던 문제

- 날짜: 2026-10-19
- 대상: `.github/workflows/refresh-data.yml` (매일 최근 7개월 재수집 → derive) · 운영 Neon Free(1GB)
- 발견: 용량 감시(`pnpm db:size`, 950MB 이상이면 워크플로 실패)가 처음으로 알림을 냈다 — 915MB → **977MB**

## 원인

갱신 한 번이 거래 테이블에 dead tuple을 약 **29만 행** 만들었다.

1. 파티션 교체: 최근 7개월(581개 파티션) 14.4만 행 DELETE 후 다시 INSERT
2. derive의 라벨 갱신: 다시 들어온 14.4만 행은 `area_type_label`이 비어 있어 전부 UPDATE → dead tuple 한 번 더

autovacuum은 기본값으로 dead tuple이 테이블의 20%(약 100만 행)를 넘어야 돈다. 그 전 3~4일 동안 지운 공간을 재사용하지 못해 매일 새 공간을 썼다. 방치하면 다음 날 1GB를 넘어 쓰기가 막힌다.

## 변경

| 변경 | 효과 |
|---|---|
| 적재 시 기존 면적 타입 범위로 라벨을 미리 채움 (`fillKnownAreaTypes`) | derive 재라벨링 144,537 → **0행**, dead tuple 절반 |
| 갱신 직후 `VACUUM (ANALYZE)` 단계 (`pnpm db:vacuum`) | 삭제 공간을 다음 갱신이 바로 재사용 — 크기가 매일 늘지 않게 |
| 즉시 조치: 운영에서 `VACUUM` 1회 (6초) | dead tuple 289,084 → 0 |

`VACUUM FULL`이 아니라 일반 `VACUUM`인 이유: 잠금 없이 돌고, 파일을 다시 쓰는 임시 공간이 필요 없다(1GB 근처에서는 FULL 자체가 한도를 넘을 수 있다). 대신 파일 크기는 줄지 않고 "늘지 않게" 만든다.

## 결과 / 남은 것

- 로컬 재현: 최근 7개월 재수집 2.3분, derive 재라벨링 0행, VACUUM 3.9초
- 운영 크기 추이는 다음 갱신들의 `db:size` 요약으로 확인한다 (기대: 977MB 근처에서 정체)
- 여유는 약 40MB로 빠듯하다. 매월 1일 24개월 재수집(약 50만 행 교체)은 한 번에 더 많은 공간을 쓴다 → 11/1 결과를 보고 Launch 전환 여부를 다시 판단
- 더 줄이려면: 내용이 바뀌지 않은 파티션은 교체하지 않기(파티션 내용 해시 비교). 갱신 시간(현재 Neon 24분)과 쓰기량이 함께 준다 — 후보

## 후속: 한도 도달 (2026-11)

- 10/20 ~ 10/31: 용량 감시가 매일 실패 알림(950MB 이상, 965MB까지)을 냈으나 대응이 늦었다 — 갱신 자체는 성공
- 11/1 24개월 재수집(약 50만 행 교체) 중 클러스터가 `neon.max_cluster_size = 1GB`에 닿았다(1,023MB). 새 페이지가 필요한 INSERT가 실패
- **악순환**: 적재 실패 → 뒤의 VACUUM 단계가 실행되지 않음 → 지운 36.5만 행의 공간을 재사용하지 못함 → 다음 날 적재도 실패. 운영 데이터가 11/2 계약분에서 멈췄다
- 원인이 로그에 없었다: 적재 스크립트가 Drizzle 오류의 `message`("Failed query …")만 찍고 실제 PostgreSQL 오류(`cause`)를 버렸다

조치:

- 워크플로: `db:vacuum` · `db:size`를 `if: always()` — 적재가 실패해도 정리 · 리포트
- 적재 스크립트: 오류의 `code` · `detail` · `cause`를 출력
- 남은 결정: 운영 VACUUM으로 일일 갱신 복구 + Launch 전환(24개월 재수집은 Free 1GB 안에서 공간이 부족)

교훈: 감시가 알림을 내도 받는 쪽 절차가 없으면 소용없다. 세션을 열 때 정기 갱신 결과를 먼저 확인한다.
