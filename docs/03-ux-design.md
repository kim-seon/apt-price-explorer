## ③ 단지 상세 (`/apartments/[id]`)

```text
┌─────────────────────────────────────────────────────────────┐
│ 🔍 검색                                    데이터 기준 10.10 │
├─────────────────────────────────────────────────────────────┤
│ 서울 > 마포구 > 아현동                                       │
│ 마포래미안푸르지오   2014년 준공                             │
│ [최근 거래] [최고가 🔺] [기간 거래 수] [3.3㎡당]               │
├─────────────────────────────────────────────────────────────┤
│ [전용 59㎡] [전용 84㎡ ●] [전용 114㎡]   기간 [최근 5년 ▾]    │  ← sticky
│                                        ☐ 해제 거래 포함      │
├─────────────────────────────────────────────────────────────┤
│ 가격 추이  (점 = 개별 거래, 선 = 월별 중위가, 🔺신고가, ✕해제) │
│ 거래량     (가격 차트와 x축 공유)                             │
│ [기간 brush] → 테이블 필터링                                  │
├─────────────────────────────────────────────────────────────┤
│ 거래 내역  N건 (선택 기간 표시) [선택 해제]                    │
│ 계약일 │ 거래가 │ 층 │ 3.3㎡당 │ 유형 │ 비고                  │
└─────────────────────────────────────────────────────────────┘
```

- 요약 → 차트 → 테이블을 수직 단일 흐름으로 배치한다.
- 해제 거래는 기본 제외. 포함 시 차트/테이블에 ✕ 마커로 표시한다.

## ② 지역 페이지 (`/regions/[code]`)

```text
서울 > 마포구 [법정동 전체 ▾]
[단지 목록] [통계] [거래 탐색]
필터: [기간 ✕] [전용 60~85㎡ ✕] [+ 필터 추가]          총 N건
테이블 (무한 스크롤)
```

- 필터 바: 적용된 필터를 제거 가능한 chip으로 표시, 추가는 popover. 모바일에서는 bottom sheet.
- 단지 목록 탭: 시군구당 수백 개 수준 → 정렬 가능한 단일 테이블.
- 통계 탭: 월별 거래량 / 중위가 차트, 법정동별 요약 테이블.

## ① 검색/진입 (`/`)

- 검색창 + 시도 → 시군구 선택. 목적은 단지 상세로 최대한 빨리 보내는 것.

## Decisions

| # | 항목 | 결정 | 이유 |
|---|---|---|---|
| 1 | 거래 탐색 테이블 | 무한 스크롤 + virtualization. 총 건수 항상 표시 | 실수요자는 페이지 점프가 아니라 정렬/필터로 좁혀서 훑는다. 잃는 것(페이지 점프)은 총 건수 표시로 보완 |
| 1-1 | pagination 구현 순서 | offset으로 baseline → 깊은 스크롤 저하 측정 → 확인되면 keyset 전환 | 전환 과정 자체를 성능 개선 사례로 기록 |
| 2 | 필터 적용 시점 | 탭/토글/프리셋은 즉시. 범위 직접 입력은 Enter·blur 시. "적용" 버튼 없음 | 입력 중 과도한 요청 방지 + 즉각적인 피드백 |
| 3 | 반응형 | 데스크톱 우선, 모바일은 사용 가능 수준 (차트 세로 스택, 테이블 핵심 컬럼, 필터 bottom sheet). 다크 모드는 Phase 3 | MVP 범위 통제 |
| 4 | 숫자 표기 | 가격 "17억 5,000" / 1억 미만 "9,500만". 단가는 전용 3.3㎡당 (헤더에 전용 기준 명시). 날짜: 테이블 "25.09.14", 차트 축 "2025.09" | 실수요자 익숙한 단위 + 기준 명확화 |

## Chart & Complex UI Enhancements

목표: "차트를 만드는 것 / 복잡한 UI를 만드는 것을 좋아한다"를 포트폴리오에서 증명한다.
원칙: 차트 개수가 아니라 깊이. ECharts 기본 기능으로 끝나는 작업만으로는 증명이 되지 않는다.

| # | 항목 | 결정 |
|---|---|---|
| A | 단지 상세 coordinated views | 기간 brush → 요약 카드 + 테이블 + URL 동시 갱신. 테이블 행 hover → 차트 포인트 하이라이트 (단방향, MVP). 양방향은 Phase 3 |
| B | 가격 분포 밴드 | 월별 중위가 선 → p25~p75 밴드 + 중위가 선. 포인트 과밀 시 점은 흐리게, 밴드 중심 표현. 분위수 계산은 서버 |
| C | 수도권 시군구 × 월 거래량 히트맵 | ① 진입 화면 검색창 아래. 셀 클릭 → 지역 페이지. "시장 분석"이 아니라 지역 선택 입구로 설계 |
| D | 차트 설계 결정 기록 | 스케일, 이상치, 색상 접근성 등 차트별 결정을 `docs/charts/`에 짧게 기록 |

### C의 조건

1. MVP의 마지막 작업. 검색 → 단지 상세 → 지역 페이지 흐름이 동작한 뒤 착수한다.
2. MVP가 지연되면 가장 먼저 Phase 3로 이동한다.
3. ECharts로 먼저 구현한다. 직접 구현(D3 / Canvas 등)은 ECharts의 한계가 실제로 확인된 후 검토한다.
4. 모바일: 최근 24개월만 표시 또는 가로 스크롤 — 구현 시 결정.

### C를 선택한 이유

- 리뷰어의 첫 화면(진입)이 강점의 증거가 된다. README 데모 GIF 소재.
- 계획된 차트 중 유일한 비표준 차트 — 색상 스케일, 행 정렬, crosshair, ~17,000 셀 렌더링 등 직접 판단할 지점이 많다.
- Frontend 성능 사례 후보를 대량 테이블 외에 하나 더 확보한다.
- 데이터는 사전 집계 가능한 작은 payload라 Backend 비용이 작다.
