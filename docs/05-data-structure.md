## 1. 면적 타입 그룹핑

### 문제

단지당 원본 전용면적 값이 여러 개다 (84.86 / 84.87 / 84.95 / 84.96 …). 사용자에게는 "84 타입" 하나로 보여야 하지만, 57.88 / 58.71처럼 실제 다른 타입일 수 있는 값도 있다.

### 후보 비교 (단지 14,211개, 316,691건)

| 규칙 | 단지당 평균 타입 수 | 0.3㎡ 미만 차이인데 분리된 쌍 | 2㎡ 이상 넓게 묶인 그룹 |
|---|---|---|---|
| 정수 내림 (floor) | 2.14 | 134 (예: 84.99 / 85.24, 28.96 / 29.11) | 0 |
| 반올림 (round) | 2.19 | 346 | 0 |
| **간격 0.5㎡ 미만이면 연결** | 2.15 | **0** | **0** |
| 간격 1.0㎡ 미만이면 연결 | 2.08 | 0 | 11 (연쇄로 23.59~25.77이 한 그룹) |
| 간격 2.0㎡ 미만이면 연결 | 2.03 | 0 | 144 |

- floor / round는 경계(84.99 vs 85.24)에서 같은 타입을 쪼갠다.
- 간격 기반은 간격이 커지면 값이 연쇄적으로 이어져 다른 타입까지 합쳐진다.

### 제안

- **단지별로 전용면적을 정렬해 인접 값 차이가 0.5㎡ 미만이면 같은 타입으로 묶는다.**
- 타입 라벨 = 그룹 내 최빈 면적의 정수부 (예: "84"). 라벨이 겹치면 A/B 접미사.
- URL에는 내부 그룹 번호가 아니라 라벨을 쓴다 (`?type=84`) → 재계산으로 그룹 번호가 바뀌어도 링크가 유지된다.
- trade-off: 새 거래가 두 그룹 사이 값을 채우면 그룹이 합쳐질 수 있다 (재계산 시 타입 변화). 적재 시 재계산하고, 변화 건수를 로그로 남긴다.

## 2. 신고가 정의

### 시뮬레이션 (마포구 전체, 해제 제외, 같은 날 거래끼리는 비교 안 함)

| 최소 선행 거래 수 | 신고가 비율 |
|---|---|
| 0 | 22.6% |
| 5 | 19.0% |
| 10 | 16.8% |

- 2018년은 그해 거래의 약 46%가 신고가. 상승장에서는 신고가가 실제로 흔하다.
- **"신고가" 배지만 붙이면 너무 흔해서 의미가 약해진다.**
- 신고가였다가 해제된 비율: 4.0% — 2020.02 이후 전체 해제율 4.6%와 차이 없음. 마포구 기준으로는 "신고가 띄우기 후 해제" 패턴의 근거가 없다 → 이 가설에 기반한 기능은 만들지 않는다.

### 제안

- 정의: 같은 (단지, 면적 타입)에서 **해제되지 않은 이전 거래(계약일 기준, 같은 날 제외)의 최고가를 초과**하고, **선행 유효 거래가 5건 이상**인 거래.
- 표현 방식 변경:
  - 테이블: 배지 대신 **"신고가 +3.2%"** (직전 최고가 대비 상승률)
  - 차트: **역대 최고가 계단선(running max)** 을 가격 차트에 추가 → 신고가가 점이 아니라 흐름으로 보인다
- 라벨: "2006년 이후 최고가" (데이터 시작 시점 명시)
- 2020.02 이전 거래: "해제 정보 없음" 안내 (해제된 거래가 기준가에 섞여 있을 수 있음)
- 계산 위치: 우선 **조회 시점 window function**으로 baseline → 측정 후 느리면 적재 시 사전 계산. (Measure Before Optimize)

## 3. 적재 (Ingestion)

### 사실

- 거래 고유 키가 없다 → 내용 기반 upsert / dedupe 불가
- 계약 → 해제 신고까지: 중앙값 25일, p95 112일, p99 203일, 최대 846일 (해제 19,481건)
- 계약 → 등기일 반영까지: 중앙값 73일, p95 142일, p99 203일, 최대 686일
- 신규 거래 신고 기한: 계약 후 30일

### 제안

- 멱등성: **(시군구, 계약년월) 파티션 단위 교체.** 한 트랜잭션에서 해당 파티션 DELETE → 받은 전체 INSERT.
- 갱신 주기:

| 작업 | 범위 | 호출 수 | 커버 |
|---|---|---|---|
| 정기 갱신 | 최근 7개월 | 83 × 7 ≈ 580 | 해제 / 등기 p99 |
| 월간 보정 | 최근 24개월 | 83 × 24 ≈ 2,000 | 해제 최대 846일까지 대부분 |
| 초기 적재 | 2006-01 ~ 현재 | 약 2.1만 | 전체 (개발계정 3일) |

- 원본 응답(XML)은 로컬에 캐시 파일로 보관 (git 제외) → 파싱 규칙이 바뀌면 API 재호출 없이 재처리. 운영 DB에는 파싱된 데이터만.
- 필수 처리: retry(타임아웃 실측 0.2%), pagination(월 최대 1,432건), 키 마스킹 로그, 빈 값 `" "` → null.

## 4. 스키마 초안 (개념)

```text
regions          시군구 83개 + 법정동 (국토교통부_전국 법정동 CSV)
  sgg_code PK, sido_name, sgg_name

complexes        거래 데이터에서 파생 (aptSeq 단위)
  apt_seq PK      — 행정구역 개편에도 불변. 앞자리로 지역 판단 금지
  name, build_year, umd_name, jibun, road_address
  primary_sgg_code — 2개 시군구에 걸친 단지 존재 → 최빈 시군구

area_types       단지별 면적 타입 (적재 시 재계산)
  apt_seq, label, min_area, max_area

transactions     약 330만 건 (수도권 전체 기간 추정)
  id (surrogate)
  apt_seq, sgg_code, umd_code
  deal_date, price (만원, int), area (전용㎡), area_type_label, floor
  cancelled (bool), cancel_date, deal_type, registered_date, apt_dong
  — 파티션 교체 키: (sgg_code, deal_date의 년월)
```

- 집계 테이블 / materialized view(월별 지역 통계, 히트맵용)는 **만들지 않고 시작**한다. 조회 패턴별 baseline 측정 후 필요하면 도입 → Phase 2 성능 사례 후보.
- index도 같은 원칙: 예상 쿼리 작성 → baseline → EXPLAIN → 결정.

## 결정 (모두 채택)

1. 면적 타입: 간격 0.5㎡ 연결 + 라벨 URL
2. 신고가: 선행 5건 이상 / 상승률 표기 / 역대 최고가 계단선 / 조회 시점 계산으로 시작
3. 적재: 파티션 교체 + 7개월 정기 / 24개월 월간 보정 + 원본 로컬 캐시
4. 스키마: 위 초안, 집계 테이블 없이 시작
